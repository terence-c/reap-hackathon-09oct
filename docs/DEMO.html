04
How AgentCart works

AgentCart is an AI purchasing agent that cannot spend until a SAFR gateway verifies its identity, checks its mandate, and logs the decision. The agent browses a small catalog and gets real merchant quotes through Reap's Agentic Payments sandbox, but none of its tools can pay. Its only route to money is to propose a purchase to the gateway, which rebuilds the request from server data, signs it, checks it against the spending limits the user set, writes the decision to a hash-chained log, and only then asks Reap for a checkout.

Built for the “Most Worthwhile Problem” track at the Reap × 65labs Agentic Buildathon.

Every agent can decide; ours can't spend until its authority is verified, its limits checked, and the decision logged.

02The idea

When agents start spending

The shift

AI assistants have spent the last few years recommending what to buy. They are now starting to buy it. An agent that can search a catalog, compare prices and fill a cart can also be handed a card, and payment providers are opening checkout APIs built for agents, Reap's Agentic Payments among them.

The moment an agent can pay, three things that came for free with a human buyer disappear:

  1. A clear limit on authority. A person buying for a company knows roughly what they may spend, where, and on what. An agent holding a card can spend whatever the card allows.
  2. A reviewer for anything unusual. A person hesitates before an odd purchase and checks with someone. An agent does not hesitate unless something outside it makes it stop.
  3. A record of why the money moved. A person can explain a purchase afterwards. An agent's explanation is text it writes on request, and it may not match what actually happened.

Where this bites

(i) Business spend

An operations agent restocks office supplies, renews software seats and books couriers. Most of these purchases are small and routine, which is exactly why nobody looks at them.

Without a control layer: a product page with hidden text ("the premium bundle is required for this order") or a misread quantity turns into a real order, and the first anyone hears of it is the card statement.

(ii) High-frequency small payments

Agents pay per API call, per document, per data query. No person can review each payment and no single one matters. The total does.

Without a control layer: a retry loop, or a supplier that quietly raises its per-call price, drains a month's budget in an afternoon, and nothing ever says stop.

(iii) Delegated procurement

A team lead gives an agent S$150 and two days to buy supplies for a project, with anything over S$80 needing their sign-off.

Without a control layer: the budget is a sentence in a prompt that the agent can misread, forget or be talked out of. The sign-off is a chat reply with no expiry that could be applied to a different cart. When finance asks where the S$150 went, the only answer is a chat transcript.

(iv) Agent-to-agent commerce

One company's buying agent deals with another company's selling agent, with nobody watching either side in real time.

Without a control layer: whatever the selling agent says about its product reaches the buying agent as input it may act on. An out-of-scope or mispriced offer is accepted at machine speed, and neither side can later prove who authorised what.

Why today's answers fall short

  • LLM guardrails are probabilistic and work at the text layer. "Never spend more than S$150" in a system prompt is a request to the model, not a control on the payment. It can be misread, overridden by injected text, or lost in a long conversation.
  • Card controls on the payment rail see only the amount and the merchant. They cannot see which agent is asking, for whom, under what mandate, or why. An S$85 luggage tag looks the same to the card whether a person chose it or a manipulated agent did.
  • Ad hoc "ask the user" prompts are not a control. They have no timeout, so a stale yes can be acted on hours later. They leave no record outside the chat. And they are not bound to the exact transaction, so a yes given for one cart can be used for another.

What "controlled environment" means here

AgentCart is a safe place to prove the pattern before any real money is involved:

  • Sandbox only. Every quote and checkout goes to Reap's sandbox (https://sg.sandbox.api.reap.global) and is paid with Reap's test cards. No real money moves.
  • The mandate lives in the application. Budget, auto-approve limit, currency, categories, dates and kill switch are stored on the server and read fresh for every decision. The model is shown them but has no way to change them. Reap's own mandates are not live in the sandbox, so this layer is ours.
  • Deterministic rules the model cannot alter. The decision is made by ordinary code with no AI in it. The same request against the same limits always gets the same answer.
  • A tamper-evident log. Every decision, refusals included, is written to a hash-chained log before Reap is asked to charge anything. Editing any saved record afterwards breaks the chain, and the app shows it.
03The idea

Who this is for

Finance and operations teams

Bounded delegation: a hard cap (S$150 in the demo) and an auto-approve threshold (S$80) that the agent cannot exceed or edit. Every decision comes with one plain sentence, for example "{amount} is above the S$80.00 auto-approve limit, so a human must approve it."

Compliance and risk

A hash-chained audit log that reconstructs any decision from the signed purchase record, the rules that fired and the reason, without trusting the agent's own account. Identity is bound to an Ed25519 signature checked against a registered public key, not to an ID string anyone can type.

The person delegating

One place to set budget, currency, categories and dates ("Edit spending limits") and one switch to stop the agent ("Pause assistant"). Escalations expire after 5 minutes if ignored, and the money held for them is released.

Payment providers such as Reap

A checkout request arrives only after the agent's authority has been verified, carries an idempotency key equal to the signed record's hash, and can be traced back to a structured intent record. That lowers dispute and fraud risk.

Developers building agents

A drop-in gate with a one-function interface, proposeCheckout({ quoteId, reason, sessionId }). The agent never handles amounts, cards or checkouts, so its code stays simple.

From hackathon demo to institution. The same four components and the same four outcomes carry over; what changes is configuration, not architecture. Thresholds, categories and merchant lists (allowedMerchants is already supported) differ per use case, reviewers become authenticated roles, and the audit log moves to storage the operator cannot quietly rewrite. New agents integrate natively by calling proposeCheckout, as AgentCart does; existing agents can sit behind the same checkpoint as a gateway that intercepts their payment calls. Either way, the payment rail only ever sees a request after the gate has said yes.

04The system

The SAFR framework

We built against the Monetary Authority of Singapore white paper "Safeguards for Agentic Finance at Runtime" (SAFR), version 1.0, July 2026, as our reference approach. It is a white paper, not regulatory guidance, and nothing in this document claims compliance with it. Where we describe what the paper asks for, that is our paraphrase, not a quotation.

SAFR in one paragraph

SAFR places a runtime governance checkpoint between every agent decision and its execution. The checkpoint has four components: Agent Identity (who is acting, and whether they may act at all), a Controls Repository (the authority the principal has delegated), a Disposition Engine (which applies those controls) and an Audit Log (which records what was decided and why). The components operate on a Governance Envelope, a structured record of the proposed action, its action trace and its context, and produce one of four outcomes: Deny Escalate Auto-Execute Observe.

Concept by concept

Governance Envelope

The idea in the paper

A structured record of the proposed action, its action trace and context metadata, filled by the checkpoint rather than the agent, and protected against change.

Our implementation

lib/safr/envelope.ts: buildEnvelope fills every field from the quote, catalog, mandate and registry; hashEnvelope (SHA-256 of canonical JSON); signEnvelope (Ed25519 over the hash). Type Envelope in lib/types.ts. The agent supplies only quoteId and reason.

Look for this in the demo

Panel section "03 · Purchase details": the latest record with a "Signed by the assistant" badge; "Technical details" shows the full JSON including context.toolTrace.

Agent Identity

The idea in the paper

Verify the agent before any other evaluation: registered, active, authentic, allowed this tool and action type, acting for this principal. An identity failure is rejected before Controls are consulted.

Our implementation

lib/safr/registry.ts (getAgent, setAgentStatus, registerPublicKey, authorizeToolCall for the tool allowlist); verifyEnvelope in envelope.ts; checkIdentity in disposition.ts. In gate.ts, decide() returns on an identity failure before the budget and velocity queries run or dispose() is called. (The mandate is loaded earlier, only to fill the envelope.)

Look for this in the demo

Step 8: "Pause assistant" then any purchase gives DENY IDENTITY_REVOKED. "Assistant details" shows agent ID, owner, AI model, instructions ID (prompt hash) and signing key fingerprint.

Controls Repository

The idea in the paper

The principal's delegated authority as bounded capability: permitted action types, decision logic, escalation conditions, validity period, principal authority, and a kill switch.

Our implementation

lib/safr/controls.ts: loadMandate, saveMandate (validates, bumps version), budget holds (reserve, settle, releaseReservation, remainingBudget), recentPurchaseCount. Type Mandate in lib/types.ts; seed lib/mandate.demo.json. Permitted action types and principal authority are on the registry record (allowed_action_types, principals).

Look for this in the demo

Step 0: "Edit spending limits". Section "02 · Spending limits" shows Budget left, Ask me above, Total budget, Currency, categories and dates. Not yet built the kill switch has no control or display in the app (step 7 uses the terminal).

Disposition Engine

The idea in the paper

Deterministic, ordered evaluation that produces the outcome. The model does not decide.

Our implementation

lib/safr/disposition.ts: dispose() is a pure function with no I/O and no LLM. Ordered checks; the first Deny wins; non-blocking rules accumulate and the strongest sets the outcome. Full order in 5d.

Look for this in the demo

Every step: the badge and the reason sentence come from here; the agent only relays them.

Audit Log

The idea in the paper

Append-only and tamper-evident; written before execution; includes rejected actions; independent of the agent's own narrative.

Our implementation

lib/safr/audit.ts: append (row hash = SHA-256 of previous hash plus canonical { seq, ts, envelope, disposition }), verifyChain, markExecuted. gate.ts appends before any checkout call. Table audit in data/safr.db.

Look for this in the demo

"05 · Activity" lists every decision, Deny included, under a "Records match" badge. Step 9: "Tamper with a record" turns it into "A record was changed".

Four outcomes

The idea in the paper

Deny, Escalate, Auto-Execute, Observe.

Our implementation

Decision in lib/types.ts: DENY, ESCALATE, AUTO_EXECUTE, OBSERVE. App labels: "Not allowed", "Needs your approval", "Allowed", "Already checked".

Look for this in the demo

Steps 1 (Auto-Execute), 2 (Escalate), 3 to 5 and 7 to 8 (Deny), 6 (Observe).

Multi-step independence

The idea in the paper

No authority carries over from one action to the next.

Our implementation

Every proposeCheckout re-reads the quote from Reap, reloads the mandate, rebuilds and re-signs the envelope and runs every rule again. An approval can be claimed once (claim() only moves PENDING forward once), and approving re-runs every rule.

Look for this in the demo

Step 6: the same book again is judged fresh and flagged VELOCITY. Test: "approval re-checks every rule: revoked in the meantime → DENY and release".

Human reviewer: timeout

The idea in the paper

A human review step needs a bounded window.

Our implementation

APPROVAL_WINDOW_MS = 5 minutes in gate.ts; expireStaleApprovals logs DENY APPROVAL_TIMEOUT and releases the budget hold.

Look for this in the demo

Step 2: the Permission card counts down from 5:00.

Human reviewer: authority

The idea in the paper

The reviewer's answer must apply to exactly what they reviewed, and be recorded.

Our implementation

The approvals table is keyed by envelope hash. approve() takes what to buy from the audit log, never from the request. A refreshed quote with a different merchant, items or currency, or a higher amount, is denied QUOTE_CHANGED. The reviewer's name is stored ("You" from the app).

Look for this in the demo

Step 2: Approve gives AUTO_EXECUTE with rules OVER_AUTO_THRESHOLD, HUMAN_APPROVED.

Integration pattern

AgentCart uses SAFR's native integration pattern: the agent itself is instrumented to emit a proposal through proposeCheckout, and the gate builds the envelope from it. The alternative, the gateway pattern, suits existing agents that already call a payment API: the checkpoint sits in the network path and intercepts those calls instead. Same four components, different insertion point. In AgentCart there is also no public route that creates a checkout (app/api/checkout/route.ts exports GET only), so the gate is the only path to Reap's checkout either way.

Where SAFR sits in the stack

Above: LLM guardrails

The system prompt (lib/agent/system-prompt.ts) and a three-tool allowlist checked by the registry on every tool call. They shape what the agent tries. Helpful, but probabilistic.

proposeCheckout({ quoteId, reason }) is the only way down

Middle: the SAFR gate

Identity, mandate, ordered rules and a hash-chained log. Deterministic. It decides whether the agent may ask Reap for a checkout at all.

POST /agentic/checkouts only after Allowed, Already checked, or a human Approve

Below: Reap

Hosted cardholder approval and sandbox settlement. The cardholder consents to this specific charge on Reap's own page; AgentCart never sees card details.

SAFR decides whether the agent may ask; Reap's page is where the cardholder consents. They are two different controls and the design keeps both.

Not yet verified In the default sandbox setup the adapter sends X-Simulate-Checkout: COMPLETED (REAP_SIMULATE_CHECKOUT defaults to true, and the header is only sent when the base URL contains "sandbox" and NODE_ENV is not production). That skips Reap's hosted approval page, so checkouts complete straight away. Set REAP_SIMULATE_CHECKOUT=false to show the hosted page: the app then shows a "Review on Reap" button and Reap returns to /orders/done?envelopeHash=…. That path is built but NOTES.md does not record an end-to-end run, so rehearse it before relying on it on camera.

What we deliberately did not implement

Being clear about the edges is part of the design:

  • Open-network identity resolution. The agent is looked up by ID in our own SQLite registry. There is no discovery of agents run by other organisations and no certificate chain to an outside authority.
  • Multiple registries. One registry, one agent (purchasing-agent-v1), one principal (demo-user-001).
  • Evidence-quality controls. The agent's stated reason is stored as data (trimmed to 500 characters) and never parsed or scored.
  • Rate limits beyond a simple velocity rule. VELOCITY flags any repeat purchase from the same merchant within 15 minutes. There are no hourly caps and no anomaly models.
  • Reviewer authentication. POST /api/approvals accepts any reviewer name of 1 to 100 characters; the app sends "You". No route has user authentication; the chat, state and tamper routes check the request comes from the same origin.
  • Independent key custody. The private key (AGENT_PRIVATE_KEY) is held by the same server that verifies it. The signature proves the record was not altered after sealing and binds it to the registered key; it does not prove a separate agent runtime produced it.
  • An external anchor for the log. The chain lives in the same SQLite file the app writes, so it is tamper-evident, not tamper-proof: someone with the file could rebuild the whole chain. Publishing the latest hash somewhere else is the next step.

5c. The Governance Envelope

The real type from lib/types.ts:

export type Envelope = {
  envelopeId: string;
  schemaVersion: "1.0";
  agent: { agentId: string; model: string; promptHash: string };
  principalId: string;
  sessionId: string;
  action: {
    type: "CREATE_CHECKOUT";
    quoteId: string;
    merchantDomain: string;
    category: string;
    items: { sku: string; quantity: number }[];
    amount: Money;
  };
  context: {
    mandateId: string;
    mandateVersion: number;
    quoteExpiresAt: string;
    toolTrace: string[];
    agentReason: string;
  };
  hash: string; // sha256 of canonical form (excluding hash + signature)
  signature: string; // Ed25519 over hash, base64
};

The agent supplies two fields: quoteId and reason. Everything else is filled on the server:

FieldFilled from

context.agentReasonAgent. Free text, cut to 500 characters, stored as data, never parsed.
envelopeId, schemaVersion, action.typeServer: a random UUID, "1.0", "CREATE_CHECKOUT".
agent.agentId, agent.model, agent.promptHashAGENT_ID and the registry record.
principalId, context.mandateId, context.mandateVersionThe stored mandate.
sessionIdThe agentcart_session cookie, passed by the tool code, not the model.
action.amount, context.quoteExpiresAtReap's quote (finalAmount, including delivery and tax), converted to integer cents.

action.category, items[].skulib/catalog.json, matched on merchant domain. An unknown merchant becomes category "Uncatalogued" and is denied on category.

From lib/safr/disposition.ts. The first Deny wins. Placeholders in braces are filled from the envelope and mandate; money is shown as S$10.79 or US$58.00.

5e. The agent's three tools

Tool (input)What it does

(category?, maxPriceCents?)		Returns items from lib/catalog.json. No network call. Out-of-scope items stay visible on purpose: seeing an item is not permission to buy it.

(sku, quantity 1 to 99)		Calls reapAdapter.createQuote, which is POST /agentic/quotes. Returns the quote in integer cents. A price, not a purchase.

(quoteId, reason 1 to 500 characters)		Calls gate.proposeCheckout with the session ID from the cookie. Returns { decision, message, approvalUrl?, checkoutId?, envelopeHash }.

Every call goes through lib/agent/router.ts (dispatchTool), which asks the registry first. Why there is no checkout tool: if the model had one, every control would depend on the model choosing to respect it. Without one, the worst a confused or manipulated model can do is ask, and asking is governed. There is no HTTP route that creates a checkout either.

5f. Request lifecycle

  1. User message. The browser posts to POST /api/agent (same-origin check, at most 40 messages, session cookie agentcart_session). The server adds the system prompt and the current spending limits read from SQLite, then streams the model with the three tools and stopWhen: stepCountIs(6).
  2. listCatalog through the router: allowlist check, a tool_calls row, catalog items back.
  3. getQuote: POST /agentic/quotes with externalCheckout: { merchantDomain, checkoutUrl } (the catalog permalink, quantity rewritten), an Idempotency-Key, DEMO_EMAIL and the demo shipping address. If Reap answers CHECKOUT_URL_INVALID, it retries with items: [{ variantId }]. Amounts become cents in toCents; merchant, SKU and quantity go into reap_quotes.
  4. proposeCheckout({ quoteId, reason }) becomes gate.proposeCheckout({ quoteId, reason, sessionId }).
  5. Re-read. The gate expires stale approvals, loads the mandate and re-reads the quote with GET /agentic/quotes/:id. It never uses numbers from the model.
  6. buildEnvelope from the quote, catalog, mandate, registry, tool trace and reason.
  7. Sign. SHA-256 of the canonical JSON, then an Ed25519 signature with AGENT_PRIVATE_KEY.
  8. Dispose. verifyEnvelope and checkIdentity first (stop here on failure), then dispose() with the mandate, remaining budget, velocity count and listed currency.
  9. audit.append: the hash-chained row is written for every decision, before any checkout call.
  10. Branch.
    • DENY returns the reason. No budget hold, no Reap call.
    • ESCALATE holds the budget and writes a PENDING approval that expires in 5 minutes. The panel shows the Permission card. Approve sends POST /api/approvals { envelopeHash, action: "APPROVE", reviewer }; gate.approve re-reads the quote (re-quotes if expired), re-seals if the quote or mandate changed, denies QUOTE_CHANGED if it differs or costs more, re-runs every rule, appends AUTO_EXECUTE with HUMAN_APPROVED and continues at step 11.
    • AUTO_EXECUTE and OBSERVE continue at step 11.
  11. Reap createCheckout. The gate holds the budget, then sends POST /agentic/checkouts { quoteId, enrollmentId, presentation: { type: "REDIRECT", returnUrl } } with Idempotency-Key = the envelope hash and returnUrl = {APP_BASE_URL}/orders/done?envelopeHash={hash}. In the sandbox it also sends X-Simulate-Checkout: COMPLETED unless REAP_SIMULATE_CHECKOUT=false. Then audit.markExecuted stores the checkout ID. If Reap fails, the hold is released and the message says nothing was charged. (Backup mode only: with DEMO_SIMULATE_WITHOUT_CARD=true and no ACTIVE card, the gate skips Reap, records a sim_… checkout ID and says so in its message.)
  12. Hosted approval, only when Reap returns nextAction.url: the chat shows "Review on Reap", the cardholder approves on Reap's page, and Reap redirects to /orders/done?envelopeHash=…. Not yet verified
  13. Poll. /orders/done calls GET /api/checkout?envelopeHash=… every 2 seconds (the chat's order card uses ?checkoutId=…). The route maps the hash to the checkout through the audit log (checkoutIdForEnvelope) and calls GET /agentic/checkouts/:id.
  14. recordCheckoutOutcome: COMPLETED settles the hold (the money counts as spent); FAILED or EXPIRED releases it. Only COMPLETED shows "Order confirmed: {orderId} · {amount}".

The return URL carries envelopeHash, not checkoutId. The hash exists before Reap answers, and the server maps it back to the checkout through its own log, so the browser never supplies the ID that gets checked.

06The demo

Get ready to run

About 10 minutes on a fresh laptop. Every command runs from the repository root.

Prerequisites

  • Node 20.9 or newer (tested on Node 24), npm, git and openssl (macOS ships one).
  • A Reap sandbox API key and the sandbox test card, both from the Reap desk.
  • An OpenAI-compatible API key for a model that supports tool calling.

git clone https://github.com/terence-c/reap-hackathon-09oct.git
cd reap-hackathon-09oct

04

Register the agent's key

npm run keygen

Registers the public key on the agent's record in data/safr.db and prints its fingerprint. If AGENT_PRIVATE_KEY is empty it mints a key pair and prints an AGENT_PRIVATE_KEY=… line: paste it into .env.local. If the variable is set it reuses it, so re-running is safe. npm run keygen -- --new always mints a new pair (the old key stops verifying).

05

Start the app on local HTTPS

npm run dev:https serves the certificate in ./certificates/ (gitignored, so a fresh clone has none). Create it once; it is valid for 30 days:

mkdir -p certificates
openssl req -x509 -newkey rsa:2048 -nodes -sha256 -days 30 -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1" \
  -keyout certificates/localhost-key.pem -out certificates/localhost.pem
npm run dev:https          # https://localhost:3443

The certificate is self-signed, so the browser warns on the first visit: choose Advanced, then Proceed to localhost. Do this once before adding a card, so Reap's redirect back lands straight in the app. The repository does not record the exact command its authors used; this one produces the same kind of certificate (RSA 2048, CN=localhost, names localhost and 127.0.0.1). Reap only sends people back to HTTPS addresses and it accepts https://localhost, so no tunnel is needed. The original plan used ngrok; NOTES.md records that Reap accepts https://localhost:3443, so it was dropped. Only if that ever changes: run a tunnel that gives a public HTTPS URL and set APP_BASE_URL to it. Plain npm run dev (http://localhost:3000) is fine for UI work but cannot add a card or complete a checkout; if another server already owns localhost:3000, open http://127.0.0.1:3000 instead (allowed in next.config.ts).

06

Add the payment card

From the app: in "01 · Payment card" click Add card. The app calls POST /api/enrollment, which creates an EXTERNAL enrollment and sends you to Reap's hosted page. Enter the Reap sandbox test card (OTP 456789 if asked). Reap returns you to /orders/enrollment-done, which polls GET /api/enrollment until Reap says ACTIVE; the panel then shows "Card ready". AgentCart never sees the card details. Each Reap link works once: if Reap says the session was used, click Start again in the panel.

From the terminal:

npm run enroll

The script creates the enrollment (this is where the enrollment ID comes from), prints Enrollment ID: … and Hosted card-entry URL: …, and waits up to 10 minutes. A person opens the URL and enters the test card; when Reap reports ACTIVE the script prints REAP_ENROLLMENT_ID=…. The enrollment is also saved in data/safr.db, so the app uses it straight away; paste the line into .env.local only for npm run smoke or another laptop.

Run the tests

npm test                   # vitest: 66 passed (6 files)

The tests use an in-memory database and the mock Reap adapter, so they never touch data/safr.db or the network.

10The demo

Find a fix

Server logs from npm run dev:https print every Reap request and response ([Reap] request, [Reap] response), plus [agentcart] and [safr] warnings.

Quote rejected

1. Quote rejected. The agent says Reap could not price the item.

Why it happens

Reap refused the merchant permalink (CHECKOUT_URL_INVALID), or the merchant is unavailable (brewlander.com returns 503 AGENTIC_SERVICE_UNAVAILABLE). The log shows [agentcart] getQuote failed for {sku}: ….

What to do

On CHECKOUT_URL_INVALID the adapter already retries with items: [{ variantId }]; that path expects Reap's own discovery variant IDs. If both fail, check checkoutUrl and variantId in lib/catalog.json against Reap's merchant sheet. Test one SKU with npx tsx scripts/quote.ts {sku}. A 503 is on Reap's side: use the step 5 fallback line.

Amounts off by 100×

2. Amounts off by 100×. The book shows S$1079.00 or S$0.11.

Why it happens

Reap sends decimal major units ({ "amount": 10.79 }); AgentCart uses integer cents everywhere else. Something read a Reap amount without converting it.

What to do

Every Reap amount must pass through ReapMoneySchema / toCents in lib/reap/money.ts. npm test covers it ("converts Reap's decimal amounts to integer cents").

returnUrl rejected

3. returnUrl rejected. "Checkout returnUrl must be HTTPS (got http://…)", or Add card fails with "Enrollment returnUrl must be HTTPS".

Why it happens

APP_BASE_URL is http://, or the app is running on plain npm run dev. Reap only accepts HTTPS return URLs; the adapter refuses before calling Reap.

What to do

Run npm run dev:https with APP_BASE_URL=https://localhost:3443 and restart after editing .env.local. No ngrok needed: Reap accepts https://localhost.

Enrollment stuck non-ACTIVE

4. Enrollment stuck non-ACTIVE. "You started adding a card. Finish on Reap…", or npm run enroll prints "Enrollment ended as …" or times out after 10 minutes.

Why it happens

Card entry not finished on Reap's page, OTP not entered, or the enrollment failed or expired. Reap rejects emails on reserved test domains such as .test.

What to do

Finish on Reap's page (OTP 456789), then "Check again" (re-reads every pending enrollment from Reap, which can take a few minutes to mark one ACTIVE). Each Reap link works once: if it says the session was used, click "Start again". Keep DEMO_EMAIL=demo@example.com.

Model not calling tools

5. Model not calling tools. Prose answers with no catalog or price cards, or a chat error.

Why it happens

OPENAI_API_KEY empty (/api/agent answers 503 "The LLM provider is not configured. Set OPENAI_* in .env.local."), a model without tool calling, or a GPT-6 model without reasoning_effort: "none".

What to do

Set the key and restart. lib/agent/model.ts adds reasoning_effort: "none" when the model name contains gpt-6. For another provider change OPENAI_BASE_URL and OPENAI_MODEL together, to a model with tool calling.

better-sqlite3 build error

6. better-sqlite3 build error. The app or a script fails on first database access.

Why it happens

npm skipped install scripts (npm config get ignore-scripts prints true), so the native module was never built.

What to do

cd node_modules/better-sqlite3 && npx prebuild-install && cd ../.., then check with node -e "new (require('better-sqlite3'))(':memory:')".

Port busy

7. Port busy. The dev server will not start, or starts somewhere unexpected.

Why it happens

An old dev server still holds 3443 (npm run dev:https) or 3000 (npm run dev).

What to do

lsof -iTCP:3443 -sTCP:LISTEN (or :3000) and stop that process. If another server owns localhost:3000, plain npm run dev also works at http://127.0.0.1:3000. If you change the HTTPS port, APP_BASE_URL must match, or Reap sends people to the wrong place.

Chain badge red with no tampering

8. Chain badge red with no tampering. "A record was changed" before step 9.

Why it happens

The Tamper button was pressed in an earlier take (the edited row stays until reset), or data/safr.db was edited or had rows deleted by hand (deleting a row breaks the chain at the next one). Recording execution status never breaks it; that sits outside the hash.

What to do

npm run reset-demo. To see where it breaks: GET /api/audit returns chain: { ok, length, brokenAtSeq }.

Also check: npm run dev:https will not start because certificates/localhost.pem or localhost-key.pem is missing or expired (create it with the command in setup step 5); every purchase says "The spending mandate is not valid right now" (dates, see section 9); every purchase says "could not be verified as coming from this agent" (AGENT_PRIVATE_KEY empty, or the public key not registered after a wipe: run npm run keygen and restart); an Allowed decision ends in "no card has been added yet" (add the card).

11The demo

Ready for the camera

Browser and layout

  • The chat and panel sit side by side only when the page is at least 1100 CSS pixels wide; narrower, they stack. At 125% zoom that is a window about 1375 pixels wide. Zoom 110% to 125% for legibility.
  • Chat on the left, SAFR panel on the right (the app does this itself above 1100 pixels). Terminal hidden; do step 7's curl off camera.
  • Use a clean browser profile: no bookmarks bar, extensions or autofill. Turn on Do Not Disturb.

Keep off screen or blur

  • REAP_API_KEY, OPENAI_API_KEY, AGENT_PRIVATE_KEY (anything showing .env.local).
  • The Reap enrollment ID: npm run enroll output, Reap's pages, server logs.
  • The test card number on Reap's hosted page.
  • Fine to show: envelope hashes, the key fingerprint, Reap checkout and order IDs, the demo email and address.

Pre-flight

  • npm run dev:https is running and https://localhost:3443 loads; the certificate warning was already accepted in this browser profile, so it never appears on camera (this replaces "ngrok up").
  • DEMO_SIMULATE_WITHOUT_CARD is false (the default) in .env.local.
  • "Card ready" in "01 · Payment card" (enrollment ACTIVE).
  • Keys loaded: header says "Assistant ready"; "Assistant details" shows a signing key fingerprint.
  • npm run reset-demo just ran, the browser was reloaded, Activity says "No records yet", Budget left is S$150.00.
  • npm test green (66 passed).
  • Clock inside the mandate dates (until 10 Oct 2026 23:59:59 Singapore time).
  • Optional: npm run smoke passes (its own in-memory database, so no reset needed afterwards).
  • One timed dry run done, then npm run reset-demo and reload again before the real take.

Backup plan if the sandbox is down

  1. Show npm test: tests/gate.test.ts runs the whole script in order against the in-memory mock adapter (Auto-execute, Escalate then approve, OVER_HARD_CAP, CURRENCY_MISMATCH, CATEGORY_OUT_OF_SCOPE, VELOCITY, identity Deny, broken chain) and asserts the audit row exists before every checkout call.
  2. Cut in a take recorded earlier while the sandbox was up.
  3. If quotes work but no card can be added: set DEMO_SIMULATE_WITHOUT_CARD=true and restart. Cleared purchases then finish as a simulated checkout (order ID SIMULATED-…, and the gate's message says no Reap order is created and no money moves). Say so on camera, and set it back to false afterwards.
  4. There is no offline mode for quotes: the gate and the agent always use the real Reap adapter, and the mock is used only by the tests.
